# Архитектурные решения (ADRs) для AI Review Analyzer

## ADR‑1: Backend API на FastAPI
**Решение:** выбран Node.js с фреймворком Express для реализации Backend API.
**Причины:** высокая производительность при I/O операциях (парсинг, запросы к API), богатая экосистема npm, возможность использовать один язык на фронтенде и бэкенде (JavaScript/TypeScript), простота разработки RESTful API.
**Альтернативы:** Flask (менее удобен для async), Django (избыточен для прототипа).

---

## ADR‑2: MySQL как основная БД
**Решение:** MySQL используется для хранения пользователей, проектов, отзывов и результатов анализа.
**Причины:** надежность, поддержка транзакций, хорошая производительность, широкое распространение.
**Альтернативы:** SQLite (подходит для прототипа), PostgreSQL (более продвинутые функции), MongoDB (не подходит для транзакционных данных).

---

## ADR‑3: Микросервисная архитектура
**Решение:** система разделена на отдельные микросервисы.
**Причины:** независимое масштабирование, изоляция сбоев, гибкость в выборе технологий.
**Альтернативы:** монолитная архитектура (проще для разработки, но сложнее для масштабирования).

---

## ADR‑4: LLM интеграция через API
**Решение:** Использование готовых LLM API (Mistral/OpenAI) для анализа тональности отзывов.
**Причины:** готовый внешний сервис, не требует локальных вычислительных ресурсов, простая интеграция.
**Альтернативы:** локальные LLM (требуют больше ресурсов), другие облачные API.

---

## ADR‑5: Wildberries парсер как часть Backend
**Решение:** Парсер Wildberries интегрирован в основной Backend как модуль.
**Причины:** упрощение архитектуры для MVP, меньше точек отказа, проще дебаггинг.
**Альтернативы:** вынос парсера в отдельный микросервис (усложняет инфраструктуру, но дает независимое масштабирование).

---

## ADR‑6: Redis для кэширования
**Решение:** Redis используется для кэширования результатов парсинга.
**Причины:** снижение нагрузки на парсер, ускорение повторных запросов, поддержка TTL.
**Альтернативы:** in-memory кэш (ограничен памятью), Memcached (менее функциональный).

---

## ADR‑7: Docker контейнеризация
**Решение:** все компоненты системы запускаются в Docker-контейнерах.
**Причины:** консистентность окружений, упрощение деплоя, изоляция зависимостей, совместимость с облачными платформами.
**Альтернативы:** виртуальные машины (более ресурсоемкие), прямое развертывание на сервере (менее переносимо).

---

## ADR‑8: Redis для асинхронных задач
**Решение:** Используем Redis для кэширования и фоновых операций.
**Причины:** Быстро (память), универсально (и кэш, и очереди), просто для MVP, проверено, TTL.
**Альтернативы:** RabbitMQ (сложнее), Kafka (избыточно), локальный кэш (не распределён).

---

## ADR‑9: Grafana + Prometheus для мониторинга
**Решение:** система мониторинга на основе Prometheus (сбор метрик) и Grafana (визуализация).
**Причины:** открытый исходный код, широкие возможности кастомизации, активное сообщество, поддержка разнообразных источников данных.
**Альтернативы:** коммерческие решения (Datadog, New Relic), облачные мониторинговые сервисы.
